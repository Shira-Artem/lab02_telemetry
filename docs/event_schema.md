# Схема игровых событий

Каждая строка `data/events.jsonl` — один объект JSON. `POST /events` принимает массив таких объектов. Время `ts` — Unix seconds в UTC; календарный день метрики D1 определяется по UTC. База хранит общие поля отдельными колонками, остальные — JSON в `payload`.

| Поле | Тип | Обязательность | Значение |
|---|---|---|---|
| `session_id` | непустая строка | всегда | Уникальная игровая сессия |
| `player_id` | непустая строка | всегда | Синтетический идентификатор игрока |
| `event_type` | enum | всегда | Одно из пяти событий ниже |
| `ts` | конечное число ≥ 0 | всегда | Время возникновения события |
| `level` | непустая строка | всегда | Игровой уровень, например `L1` |
| `x`, `y` | числа | `death`, `checkpoint` | Координаты в диапазоне карты 0–100 для демонстрационных данных |
| `cause` | непустая строка | `death` | Причина смерти |
| `time_s` | число ≥ 0 | `level_complete` | Время до завершения уровня, секунды |
| `reason` | непустая строка | `session_end` | Причина окончания |

Типы событий: `session_start` открывает сессию; `death` обозначает гибель; `checkpoint` — достижение контрольной точки; `level_complete` — прохождение уровня; `session_end` закрывает сессию. События одной сессии имеют одинаковые `session_id` и `player_id`. Порядок задаётся `ts`. Воронка засчитывает этапы только при последовательности `session_start → checkpoint → level_complete` в пределах одной сессии и уровня; одновременные timestamps считаются допустимыми.

Пример:

```json
{"session_id":"demo_42_001","player_id":"player_01","event_type":"death","ts":1788285650.0,"level":"L1","x":28.4,"y":35.1,"cause":"spikes"}
```

API отвечает `202` с числом новых записей `accepted`. Повторная отправка события с теми же `session_id`, `event_type`, `ts`, `level` идемпотентна. Неверные поля или типы дают `422`; пустой пакет — `400`.
